# 暗黑3 式符文系统 — 可行性调研（Crystal / Mir2）

> 结论：**可实现**。这套代码把技能逻辑高度集中在少数几个"漏斗"上，
> 数值类改造几乎可以一处生效；形态类改造需要逐技能写变体，但变体代码全部写进独立模块（`RuneBehaviors/`），每个符文新增 1 个文件即可。
> 客户端 UI 是纯代码手绘对话框，新增技能符文面板没有框架障碍；美术可以从"复用现有图库帧"起步，零美术也能先跑通。

## 1. 现有代码的关键"插槽"（带位置证据）

### 1.1 技能数据与玩家技能实例

| 内容 | 位置 |
|---|---|
| 技能模板 `MagicInfo`（名称/耗蓝/等级/威力/倍率/冷却/范围） | `Server/MirDatabase/MagicInfo.cs:9` |
| 玩家技能实例 `UserMagic`（Spell / Level / Key / Exp / CastTime） | `Server/MirDatabase/MagicInfo.cs:86` |

| 数据库版本号（当前 117） | `Server/MirEnvir/Envir.cs:56` `public const int Version = 117` |

### 1.2 服务端技能派发漏斗（最重要）

- `HumanObject.Magic(...)`：`Server/MirObjects/HumanObject.cs:3401`
  一个 `switch (spell)` 把 130 个技能分派到 67 个处理函数（`Fireball` / `HellFire` / `FireWall` / `Blizzard` ...）。
  符文要做"形态改变"，基本都在这 67 个函数里加分支。
- 延迟结算漏斗：`DelayedType.Magic` → `CompleteMagic(...)`：`Server/MirObjects/HumanObject.cs:5904`
  有效伤害/中毒/反弹/回血都在这里落地 → "命中后触发"类符文（爆炸、连锁、吸血、留地火）挂这里最省事。

### 1.3 数值计算的集中点（这是本方案最大的利好）

技能数值几乎全部走 `UserMagic` 的这 4 个方法：

| 方法 | 位置 | 覆盖范围 |
|---|---|---|
| `GetDamage(int)` | `MagicInfo.cs:197` | 全仓库技能伤害调用 **57 处**（`magic.GetDamage(...)`） |
| `GetPower()` / `GetPower(int)` | `MagicInfo.cs:206` / `MagicInfo.cs:229` | 护盾/回复/召唤类威力（MagicShield、ProtectionField、Healing…） |
| `GetMultiplier()` | `MagicInfo.cs:202` | 技能成长倍率 |
| `GetDelay()` | `MagicInfo.cs:243` | 技能冷却 |
| `HumanObject.MagicCost(UserMagic)` | `HumanObject.cs:3376` | 耗蓝（已有 ManaPenalty 等修正先例） |

也就是说：**"加伤害 / 加范围 / 减冷却 / 减耗蓝 / 改倍率"这类符文，在 2~3 个方法里插符文修正就能覆盖全部 130 个技能**，不需要逐个改。

### 1.4 状态 / 临时增益的现成设施

- Buff 系统：`Server/MirDatabase/BuffInfo.cs:6`（BuffInfo）与 `BuffInfo.cs:90`（Buff），
  带 `Dictionary<string, object> Data` 自由字段 + `Stats` + `BuffStackType`（叠加/刷新/无限）。
  → "下次施法强化"、"叠 5 层爆炸"、"持续 X 秒"这类机制可直接复用，无需新造轮子。
- 可选状态同步先例（**符文选择的最佳抄写对象**）：
  - 客户端发包：`Shared/ClientPackets.cs:1495` `SpellToggle { Spell, canUse }`
  - 服务端处理：`Server/MirNetwork/MirConnection.cs:1650` → `HumanObject.SpellToggle(...)`（`HumanObject.cs:8502`）
  - 落库：`CharacterInfo.cs:70` `public bool Thrusting, HalfMoon, ...`（随存档持久化）
  → 符文选择完全可以照这条路：一个 `C.SetRune` + `HumanObject.SetRune` + 存档字段 + `S.SetRune` 广播。

### 1.5 协议与版本

- 包注册：`Shared/ClientPackets.cs`、`Shared/ServerPackets.cs`、`Shared/Packet.cs`（`case (short)ClientPacketIds.X`）
- 客户端版本只做 **MD5 校验**：`Server/MirNetwork/MirConnection.cs:836`（`Settings.CheckVersion` / `VersionHashes`）
  → **客户端与服务端一起发版时，协议可以自由改**，无需为旧客户端做兼容分支。
  ⚠️ 但**存档格式**（`Server.MirDB`）必须用版本守卫，现有写法见 `UserMagic.Save` / `UserMagic(reader, version, customVersion)`（`MagicInfo.cs:100`、`MagicInfo.cs:112`）里的 `if (version < 65) return;` 之类。
- 登录时技能下发：`S.UserInformation.Magics`（`Server/MirObjects/PlayerObject.cs:1693`）+ 单个 `S.NewMagic`（`MagicInfo.cs:148`）。

## 2. 方案设计

### 2.1 数据模型（服务端 `RuneInfo`，存 `Envir/Rune/Runes.json`）

> ⚠️ 本节是**效果参数清单**（数据长什么样）；文件位置与模块归属以**第 6 节 v2 架构为准**：
> 符文定义存 JSON（不进 `Server.MirDB`、不改 DB 格式），角色选择/解锁存 `RuneBook`（自带版本头）。

```csharp
public class RuneInfo            // 一个技能有 3~5 个符文，D3 风格：同时只带 1 个
{
    public int Id;               // 全局唯一
    public Spell Spell;          // 归属技能
    public byte Slot;            // 1..5，同技能内排序
    public byte Icon;            // 图库帧索引
    public byte NeedMagicLevel;  // 需要该技能达到的等级才解锁
    public RuneEffect Effect;    // [Flags] 效果位（见下）
    // 数值参数（用不到的留默认即可，纯数据驱动）
    public float DamagePct, CostPct, CooldownPct, RangeBonus;
    public int DamageFlat, ExtraTargets, ExtraDuration, ProcChance;
    public Spell VisualSpell;    // 非 None 时客户端用这个技能的特效表现（复用现成特效）
    // 上 Buff 类符文（如首个符文：攻速+5）
    public BuffType BuffType;
    public Stats BuffStats;      // 例：{ [Stat.AttackSpeed] = 5 }
    public int BuffDurationMs;
    // 描述文案走多语言 key：Rune_{Id}_Name / Rune_{Id}_Desc
}

[Flags] public enum RuneEffect {
    None = 0,
    DamageUp, DamageDown, CostDown, CooldownDown, RangeUp,
    ExtraTargets, Pierce, Chain, ExplodeOnHit, SplashRing, LeavePuddle,
    HealOnHit, ShieldStack, SummonVariant, TransformProjectile, ...
}
```

- 注册表：由 `RuneRepository` 读取 `Envir/Rune/Runes.json`（首次启动自动生成模板文件），**不再往 `Envir.RuneInfoList` / `Server.MirDB` 里塞** → DB 格式零变更，改完重启或热重载即可生效。
- 校验：启动时检查 Spell 是否存在 / Slot 是否重复 / BuffType 是否合法 / BehaviorId 能否解析；失败只记 warning 不报错（数据先行、代码后补不会炸服）。
- 编辑：先手改 JSON；后续可选 `Server.MirForms/Database/RuneInfoForm`（读写同一个 JSON，参照 `MagicInfoForm`）。

### 2.2 玩家侧数据

- `UserMagic` 增 `byte RuneId`（0 = 无符文），`Save/Load` 用 `if (version > 117)` 守卫；老档默认 0。这是符文系统**唯一**落在数据模型上的字段（原因见 6.5：`GetDamage()` 拿不到「拥有者」引用）。
- `CharacterInfo` 增 `RuneBook Runes`（解锁集合 + 各技能当前选择 + 运行时状态），`RuneBook` 自带二进制版本头 —— **以后给符文加字段只改 `RuneBook.cs`，不再动 `CharacterInfo`**。
- 解锁与选择分离：解锁是「永久拥有」，选择是「当前生效 1 个/技能」（D3 式）。

### 2.3 服务端计算层（分层，避免大改 67 个函数）

> ⚠️ 本节的"什么效果"沿用；但"改哪里"已全部收敛到**第 6 节 v2 架构的 15 处钉子** ——
> 尤其**行为层/触发层的代码一律写在 `Server/RuneSystem/RuneBehaviors/` 里，不在原 spell 函数里加分支**。

1. **数值层（一处生效，覆盖全部技能）**
   在 `UserMagic.GetDamage / GetPower / GetMultiplier / GetDelay` 里叠加当前符文修正；
   `HumanObject.MagicCost(...)` 里叠加耗蓝修正。委托给 `RuneFx.Apply(magic, ref value, RuneEffect.DamageUp)` 之类的helper。
   → 阶段 1 就能让每个技能拥有"强化/削弱/省蓝/减 CD"符文。

2. **行为层（按技能写分支）**
   在各 spell 函数里 `if (RuneFx.Has(magic, RuneEffect.ExtraTargets)) { ... }`。
   例：
   - `Fireball`（`HumanObject.cs:3940`）→ 3 连发 / 穿透 / 命中溅射
   - `HellFire`（`HumanObject.cs:4104`）→ 改扇形角度或改环形
   - `FireWall`（`HumanObject.cs:4150`）→ 改成一圈 / 加长
   - `Healing`（`HumanObject.cs:4360` 区）→ 群体化 / 附加护盾
   - `ProtectionField`、`MagicShield`、`Blizzard`、`MeteorStrike` 同理
   每个技能 10~40 行，代码量可控。

3. **结算/触发层**
   `CompleteMagic(...)`（`HumanObject.cs:5904`）里加 `switch (magic.RuneId)` 做"命中后"逻辑（爆炸、连锁、吸血、留地火、给 Buff）。复用 Buff 系统和 `Poison`/`SpellObject`。

4. **校验**：所有修正只在服务端算；`SetRune` 必须校验（拥有技能/符文归属/解锁/等级），客户端只负责展示，不识破改包。

### 2.4 协议（新增，不改老的 `ClientMagic`）

⚠️ 注意：`ClientMagic(BinaryReader)`（`Shared/Data/ClientData.cs:19`）**没有版本号参数**，
往里加字段会让旧存档/旧包解析错位。所以推荐：

- 新增 `C.SetRune { Spell, RuneId }`
- 新增 `S.SetRune { ObjectID, Spell, RuneId }`（登录后与切换时下发，广播给周围用于表现）
- 新增 `S.RuneList { RuneInfo[] }`（登录时一次性下符文表：Id/Spell/Icon/名称/描述/参数）
  —— 也可以把"当前选择的 RuneId"塞进 `S.NewMagic` 的新字段（因为协议可随客户端一起改），
  但独立的 `S.RuneList` 让客户端能提前画好整个符文面板，交互更顺。
- 施法表现：`S.Magic` / `S.ObjectMagic` 增加 `byte RuneId`（或 `Spell VisualSpell`），客户端 `PlayerObject` 的 `switch (Spell)` 里按变体选特效。

### 2.5 客户端 UI

1. **入口**：`CharacterDialog` 技能页每个 `MagicButton` 增加一个小「符」按钮（复用 `Prguse` 现有按钮帧），点击打开符文面板。
2. **`RuneDialog`**：D3 风格 —— 左侧技能图标+名称+当前符文，右侧 5 个符文格子（图标 / 名称 / 描述 / 数值变化 / 未解锁态灰化）。
   控件全部用现有 `MirImageControl / MirLabel / MirButton` 拼装，不需要新框架。
3. **技能栏提示**：`SkillBarDialog` 的 `Hint` 追加"符文：XXX（伤害 +25%）"；格子右下角画符文角标（小图标叠加，`MirControl.Draw` 支持混合）。
4. **表现变体**：`PlayerObject.cs` 施法特效 `switch` 里按 `RuneId` 选 `Effects.Add(new Effect(Libraries.MagicX, ...))`。
5. **多语言**：`ClientTextKeys` / `ServerTextKeys` 增 key，`Client/Localization/*.json`、`Server/Localization/*.json`、
   以及 `Build/Client/Release/Localization/*.json`、`Build/Server/Release/Localization/*.json` 同步（仓库里这几个副本都在用）。

## 5. 定稿决策（2025 调研结论）

| 决策项 | 结论 |
|---|---|
| 绑定模型 | **暗黑3 式：每个技能 3~5 个符文，同时只有 1 个生效**，可随时切换 |
| 首期范围 | **战士 · 基本剑术（`Spell.Fencing` = 1）**，只做 **1 个符文** |
| 首个符文效果 | 攻击命中时 **100% 概率**（数值留成可配，后期再调）给自己加一个 Buff：**攻击速度 +5** |
| 是否开工 | 暂不实现，仅保留本调研 + 实施方案 |

> 选"基本剑术"作为第一个很合适：它是被动技能，不走 `Magic()` 的 switch，
> 逼着我们第一版就把「**被动技能符文 → 战斗事件触发 → 上 Buff**」这条真正的符文骨架打通，
> 而不是图省事只做数值乘法。这条骨架正好是后面所有符文的公共基础设施。

### 5.1 这个符文能不能做：能，而且几乎不需要新机制

三段链路在代码里都有现成设施：

| 环节 | 现成设施 | 位置 |
|---|---|---|
| 攻击事件钩子 | `HumanObject.Attack(dir, spell)` 内的命中循环里已经有 FatalSword / MPEater / Hemorrhage 这种"命中触发"区段 | `Server/MirObjects/HumanObject.cs:2849`，触发区段 ≈ `3060~3135` |
| 加 Buff | `AddBuff(BuffType, owner, duration, Stats, refreshStats)`，直接用 `new Stats { [Stat.AttackSpeed] = 5 }` | `HumanObject.cs:7461`；范例见 `HeroObject.cs:388`（用 `BuffType.Storm` 带 `AttackSpeed`） |
| 攻速生效 | `AddBuff` 默认 `refreshStats: true` → `RefreshStats()` 先 `RefreshBuffs()` 汇总 Buff 的 Stats，再 `AttackSpeed = 1400 - (Stats[AttackSpeed]*60 + min(370, Level*14))`（下限 550） | `HumanObject.cs:1731`、`:1747`、`:1767` |
| Buff 图标/描述 | 服务端 `BuffInfo`（`Visible=true` 才会广播给周围）+ 客户端 `BuffImage(BuffType)` 图标映射 + `BuffString(BuffType)` 文案 + 多语言 key `BuffType_XXX` | `Server/MirDatabase/BuffInfo.cs:6`；`Client/MirScenes/Dialogs/BuffDialog.cs:416`、`:277`；`Shared/Language.cs:4136`（`typeof(BuffType)` 自动生成 key） |

**注意**：`Stat.AttackSpeed` 每 1 点 = **减少 60ms 出手间隔**（`1400 - stat*60 - min(370, level*14)`，最低 550ms）。
+5 → 约 **-300ms**，对低级角色是 25%~40% 的攻速提升，明显偏强；建议第一版就用"可配置字段"，上线前实测再调（改数值即可，不用改代码）。
如果后期想要"攻速 +5%"，现有代码**没有百分比攻速通道**（`Stat.AttackSpeedRatePercent` 只乘 `Stats[AttackSpeed]` 本身，纯 Buff 里没基数就是 0），需要在 `RefreshStats` 的 `AttackSpeed` 计算后追加一行百分比修正。

### 5.2 需要落地的改动清单（阶段 0 · 这份清单即工作量）

### 5.4 这一刀的风险清单

1. **BuffType 插入位置**：最容易踩且后果最隐蔽（老档 Buff 错乱）。必须追加在未占用段。
2. **存档版本升级**：`Server.MirDB` 117→118，老档 `RuneId`/`UnlockedRunes` 必须兜底；先在测试库上跑一遍。
3. **一记平砍多目标**：`Attack` 的命中循环会遍历多个目标，触发点必须节流，否则叠加/刷新频率不符合预期。
4. **攻速数值过强**：+5 = -300ms 是硬数值，建议先给 1~2 起，且写进数据表而非硬编码。
5. **Buff 会随存档保存**：如果这个 Buff 是短时 proc Buff，考虑加 `BuffProperty.RemoveOnExit`，避免下线后重登还挂着。
6. **英雄**：`HeroObject` 复用 `HumanObject.Attack`，符文按 `UserMagic.RuneId` 判定，英雄默认为 0 即不触发——但若将来给英雄开符文，需要单独 UI 与解锁数据。

## 6. 低侵入 / 可扩展架构（v2 定稿）

> 硬要求：符文系统作为一个**相对独立的模块**存在，不把符文逻辑散进原有技能代码，且以后加符文不需要再改原有文件。
> 本章是权威架构，**第 2.3 / 2.4 / 5.2 节的实现位置以本章为准**（那些章节描述的是"效果清单"，不是"代码落点"）。

### 6.0 一句话概括

> 原有代码只暴露 **15 个文件、合计约 40 行的"钉子"（seam）**，全部是"加一行调用 / 加一个字段 / 加一个 case"；
> 符文的一切业务逻辑（数据、校验、数值、行为、触发、UI、存档结构）全部住在**新目录**里。

### 6.4 可扩展性：四层，从"最省事"到"最自由"

| 层 | 谁来做 | 加一个新符文要做什么 | 覆盖比例（预估） |

| **L2 行为插件** | 程序 | 在 `RuneBehaviors/` 加 1 个实现 `IRuneBehavior` 的文件（反射自动注册），需要动原技能时用 `HumanObject.RuneExt.cs` 的包装调原私有函数 | ~30% |

配套设计细节：
- `IRuneBehavior` 接口（全部事件都可选实现，空实现零成本）：
  ```csharp
  public interface IRuneBehavior
  {
      int RuneId { get; }                                   // 或由 attribute 指定
      void OnSwing(RuneContext ctx) { }
      bool TryCast(RuneContext ctx) => false;               // true = 接管，跳过原技能
      bool OnMagicComplete(RuneContext ctx, IList<object> data) => false;
      void OnDealtDamage(RuneContext ctx, MapObject target, ref int damage) { }
  }
  ```
  `RuneContext`（struct / 复用对象）只带 `Owner / Magic / RuneInfo / Direction / Location / Target / Time`。
- `RuneBehaviorRegistry` 启动时反射扫描 `typeof(IRuneBehavior)` 的实现并缓存委托，`Runes.json` 里用 `BehaviorId` 引用；
  找不到实现时不报错（降级为纯数据效果 + 记日志），**符文数据先行、代码后补也不会炸服**。
- `Runes.json` 热重载：`RuneRepository.Load()` 可被 GM 命令/文件监听再次调用，切换只重建缓存，不动在线角色状态。

### 6.5 性能与线程安全（战斗热路径）

- `RuneHooks.*` 第一行永远是 `if (magic.RuneId == 0) return value;` —— 无符文玩家全程零额外开销。
- 每角色一份只读 `RuneRuntime` 快照，切换符文时才重建；战斗路径只做数组/字典查表，不分配、不加锁。
- `UserMagic.RuneId` 放在 `UserMagic` 上（而不是每次靠 `RuneBook` 查字典），正是因为 `GetDamage()` 拿不到"拥有者"引用 —— 这是 6.3-S2 那个字段存在的唯一原因。
- `RuneBook` 用 `byte` 存 `Spell`、`ushort` 存 `RuneId`，单角色 < 1KB。

### 6.6 安全性

- 符文修正**只在服务端计算**；`Runes.json` 不下发客户端，客户端只收到"该技能当前符文 id + 展示文案"。
- `SetRune` 校验链：拥有该技能 → 符文归属该技能 → 已解锁 → 技能等级达到 `NeedMagicLevel` → 请求频率节流；任一失败直接回 `S.SetRune` 原值（客户端回滚高亮）。
- 客户端符文面板只做展示与请求，不参与任何数值。

1. 把 6.3 的 15 处写进 `docs/rune-hooks.md`（含行号与代码片段），**以后新增符文不允许修改此清单外的文件**。
2. 一条命令即可验证模块边界是否被破坏（应为空输出）：
   ```bash
   grep -rn "RuneRepository\|RuneBook\|IRuneBehavior\|RuneInfo\b" Server --include=*.cs | grep -v "Server/RuneSystem"
   ```
3. Code review 检查项：新增的符文相关 `using Server.RuneSystem;` 只能出现在 6.3 列出的文件里。

### 7.4 暴击类符文：能不能直接用现有的暴击率 / 暴击伤害属性？

**结论：暴击伤害可以直接复用；暴击率不行（有职级上限），必须走一个 1 行门面把判定强制为真。**

游戏现有实现（普攻与技能共用，两处：`HumanObject.Attacked`、`MonsterObject.Attacked`）：

```csharp
// 暴击判定（百分比）
if (Envir.Random.Next(100) < (attacker.Stats[Stat.CriticalRate] * Settings.CriticalRateWeight))
{
    // 暴击伤害：在最终伤害上追加
    damage += floor(damage * ((attacker.Stats[Stat.CriticalDamage] / Settings.CriticalDamageWeight) * 10));
}
```

| 项 | 现值（`Configs/Setup.ini`） | 换算 |
|---|---|---|
| `CriticalRateWeight` | 5 | 暴击率% = `CriticalRate × 5` |
| `CriticalDamageWeight` | 50 | 暴击总伤害% = `100 + CriticalDamage × 20` |

**暴击伤害 —— 可以直接用**：
`CriticalDamage = 5` → `100 + 5 × 20 = 200%`，与需求完全吻合。
所以符文数据里写 `CritDamagePct: 200`，载入时按 `CriticalDamageWeight` 反算成 `Stat.CriticalDamage`（`50 × (200-100) / 1000 = 5`），
**管理员改 Setup.ini 的权重也不用改符文数据**。

**暴击率 —— 不能只用属性**：
`Shared/BaseStats.cs` 给所有职业设了 `Caps[Stat.CriticalRate] = 18`，而 `RefreshStatCaps()` 每次 `RefreshStats` 都会 clamp，
18 × 5 = **最高 90%**，堆不满 100%。而且这个上限是全局的（物品/宝石同样受限），**不该为了一个符文去改全局上限**。

所以实现方式是：在暴击判定里"或"上一个门面
```csharp
if (Envir.Random.Next(100) < (attacker.Stats[Stat.CriticalRate] * Settings.CriticalRateWeight) || RuneEvents.ForceCritical(attacker))
```
`ForceCritical` 只做一件事：判断该玩家身上"必暴符文"的 Buff 是否还有次数。
这样暴击特效、暴击飘字、暴击伤害公式全部沿用原版，客户端一行都不用改。

**次数（下 3 次攻击）怎么算**：
- `OnSwing`（挥砍）时若没有 Buff → 直接补满 3 次；
- `OnDealtDamage`（真正造成伤害后）→ 次数 -1，减到 0 就移除 Buff；
- 落空的挥砍不扣次数（符合"下 3 次攻击"的直觉）；
- 次数写在 `Buff.Values[1]`，客户端 Buff 提示里会显示"剩余次数: N"。

实测（服务端日志，`armour=2`）：
```
force check rune=3 charges=3 → CRIT forced=True  7->14  stat=5  dealt=12
force check rune=3 charges=2 → CRIT forced=True  6->12  stat=5  dealt=10
force check rune=3 charges=1 → CRIT forced=True 10->20  stat=5  dealt=18
force check rune=3 charges=3 → CRIT forced=True  9->18  stat=5  dealt=16   ← 次数用尽后重新挂 Buff
```

> 注意：由于 `ProcChance = 100`，这个符文实质上是"3 连暴 → 1 次普通 → 3 连暴"的循环常驻。
> 想做成稀有触发，把 `ProcChance` 调低（例如 20）即可，不需要改代码。

### 7.5 连击类符文（攻杀·连斩）实现说明

需求：**攻杀剑术命中时 100% 概率立刻再释放一次攻杀剑术，且不占用普通攻击的 CD。**

实现方式：行为里直接再调一次原版 `HumanObject.Attack(dir, Spell.Slaying)`，因此第二刀是完全真实的技能一击
（同样的命中判定、伤害公式、暴击判定、技能动画），**没有复制任何技能逻辑**：

```csharp
long atkCd = owner.AttackTime;      // 这一刀已经算好的冷却
long actionCd = owner.ActionTime;

owner.Slaying = true;               // 攻杀"就绪"标记已被第一刀消耗，这里补回去，保证第二刀仍是攻杀
owner.AttackTime = 0;               // 临时清零才能通过 CanAttack 检查
owner.ActionTime = 0;

try { owner.Attack(dir, Spell.Slaying); }
finally
{
    owner.AttackTime = Math.Max(owner.AttackTime, atkCd);   // 恢复成"只算一次攻击"的冷却
    owner.ActionTime = Math.Max(owner.ActionTime, actionCd);
}
```

要点：

1. **不占 CD 是天然成立的**：两次挥砍在同一个服务器 tick 内完成，`Envir.Time` 不变，
   所以两次 `AttackTime = Envir.Time + AttackSpeed` 结果相同；再叠加 `Math.Max` 恢复，等于只打一刀的冷却。
2. **重入保护**：第二刀自己也会走 `RuneEvents.OnSwing`，用 `HumanObject.RuneRepeatGuard` 保证只连一次
   （`RepeatCount` 可配 >1 做多连）。
3. **零新增钉子**：完全复用 6.3 里已登记的 `OnSwing` 门面，属于"加文件即可"的 L2 扩展。

实测（`Tools/RuneTestTool --smoke --spell Slaying --rune 4 --repeat`）：

```
挥砍 20 次：命中 11 次，其中一次攻击打出 2 下 3 次      ← 3/11 ≈ 攻杀就绪概率(33%)，命中即连击
冷却探测（相对这次连击）：+600ms 挡，+1700ms 接受        ← 冷却仍是一次攻击≈1.3s，没有被翻倍
```

> 注：仅当这一刀"真的是攻杀剑术"时才触发（原版里攻杀有随机的就绪判定，未就绪的攻击按普通攻击结算）。
> 这就是 3/11 而不是 11/11 的原因；如果想让连击概率独立于就绪判定，把 `ProcChance` 与就绪判定解耦即可（属于数值层调整）。

### 7.6 破防 / 最大攻击类符文（攻杀·破军）实现说明

需求：**本次攻杀按角色最大攻击力计算，并且忽视目标防御。**

这两件事都在原版伤害流程里各有一个明确的位置，所以只用 2 个"一行门面"就够，不需要改伤害公式：

| 需求 | 原版位置 | 门面 |
|---|---|---|
| 按最大攻击计算 | `int damageBase = GetAttackPower(Stats[Stat.MinDC], Stats[Stat.MaxDC])`（`HumanObject.cs:2984`） | `RuneHooks.ApplyMaxAttack(this, spell, ref damageBase)` → 命中时 `damageBase = Stats[Stat.MaxDC]` |
| 无视目标防御 | 每目标结算前的 `DefenceType defence`（`HumanObject.cs:3204` 前） | `RuneHooks.ApplyIgnoreDefence(this, spell, ref defence)` → 把 defence 改写成"护甲为 0"的类型 |

**`DefenceType` 的选择（这是唯一需要设计的点）**：`MapObject.GetArmour` 里

| 类型 | 护甲 | 命中判定 |
|---|---|---|
| `ACAgility`（默认） | MinAC~MaxAC | 敏捷闪避 |
| `Agility` | **0** | 仍可被敏捷闪避 |
| `None` | **0** | 必中 |

数据里用 `GuaranteedHit` 切换：默认 `false` → `DefenceType.Agility`（**只忽略防御值，仍可能被闪避**，最贴近"忽视防御"的字面含义）；
把它设为 `true` 则连命中判定一起跳过（`DefenceType.None`，必中）。

数据（`Envir/Rune/Runes.json`）：

```json
{ "Id": 5, "Spell": "Slaying", "Slot": 2, "Name": "攻杀·破军",
  "Description": "本次攻杀按角色最大攻击力计算，并无视目标防御（AC）。",
  "Effect": "MaxAttackOnHit, IgnoreDefence", "ProcChance": 100 }
```

没有 `BehaviorId` —— 纯能力位 + 门面，**不新增行为文件**。

**`ProcChance` 也支持**（`MaxAttackOnHit` / `IgnoreDefence` 属于"每次出手"能力位）：
`RuneEvents.OnSwing` 在每次挥砍时掷一次骰，把结果记在 `HumanObject.RuneProcRuneId/RuneProcRuneResult`，
`ApplyMaxAttack` 与 `ApplyIgnoreDefence` 都只读这次结果 —— 因此同一刀的所有目标，
要么"最大攻击 + 破防"同时成立，要么同时不成立，不会出现半生效。

实测（`--smoke --spell Slaying --rune 5 --maxatk`）：

```
[RuneDebug] maxattack spell=Slaying base 7 -> maxDC 14 (minDC=4)
[RuneDebug] ignoredefence spell=Slaying ACAgility -> Agility

无符文: [10,10,9,4,8,2,12,11,9,3]   均值 7.8  最高 12
带符文: [14,14,14,7,8,8,14,10,14,2] 均值 10.5 最高 14
```

> 样本里仍有低值（2、3、7、8），因为原版攻杀剑术有随机"就绪"判定（约 1/3 概率），
> 未就绪的攻击按普通攻击结算，不吃符文加成 —— 与连击符文的表现一致。

### 7.7 `ProcChance` 的作用范围（触发概率）

`ProcChance`（0~100，默认 100）由 `RuneEffects.TryProc()` 统一掷骰：

| 取值 | 行为 |
|---|---|
| `>= 100` | 必定触发（不掷骰，零开销） |
| `<= 0` | 永不触发（等于临时关掉这个符文，但符文仍显示在面板里） |
| 1~99 | `Random.Next(100) < ProcChance` |

**目前会掷骰的能力位**（都是"每次出手/每次命中"型）：

| 能力位 | 符文 | 掷骰时机 |
|---|---|---|
| `BuffOnSwing` | 剑术·疾风 | 每次挥砍 |
| `GuaranteedCritical` | 剑术·蓄势 | 每次挥砍（仅补 Buff 时） |
| `RepeatCastOnSwing` | 攻杀·连斩 | 每次攻杀挥砍 |
| `MaxAttackOnHit` / `IgnoreDefence` | 攻杀·破军 | 每次挥砍（一次掷骰，所有目标共用） |
| `HealOnDealtDamage` | 剑术·饮血 | **每个伤害事件**（多目标会逐目标掷骰，与上面几个不同） |

**不会掷骰的能力位**：纯面板数值修正（`DamageUp/DamageDown/DamagePct/DamageFlat/
CostPct/CooldownPct/PowerPct/PowerFlat`）—— 它们在 `UserMagic.GetDamage/GetPower/GetDelay`
和 `MagicCost` 里生效，属于"数值恒常修正"，没有触发概念。

> 破军的 `ProcChance` 实测（同一只蝎子，各 20 次命中）：
>
> | ProcChance | 最高伤害 | 峰值 14 出现 | 均值 |
> |---|---|---|---|
> | 0 | 12 | 0/20 | 6.5 |
> | 100 | **14** | **8/20** | 10.1 |
>
> 14 = 角色 MaxDC，且护甲为 0 —— 说明"最大攻击 + 破防"确实被 `ProcChance` 精确控制。

### 7.8 符文生效时的着色表现（攻杀·破军 → 金黄）

需求：符文生效时给技能加"着色器"样的效果，例如破军触发时把攻杀染成黄色。

调研结论：**原版没有现成的着色管线，但已经有两个可复用的着色入口**，不需要引入 shader：

| 入口 | 位置 | 说明 |
|---|---|---|
| 角色本体着色 | `MapObject.DrawColour` + `ApplyDrawColour()` | 原本被中毒状态复用来染色（红/绿/紫/灰…），绘制时才读取，所以外部设置的着色不会被每帧重算覆盖 |
| 技能特效着色 | `PlayerObject` 里的 `Libraries.Magic.DrawBlend(帧, 坐标, Color.White, ...)` | 第三个参数就是顶点调制色，把 `Color.White` 换成变量即可染色 |

实现（**多一层"着色通知"包，其余全是读缓存的绘制代码**）：

```
服务端：破军掷骰成功 → RuneEffects.SendProcVisual(ctx)
        → S.RuneProc { ObjectID, Spell, RuneId, TintArgb, TintMs }（本人 Enqueue + 周围 Broadcast）
客户端：GameScene 收到包 → RuneVisuals 记录 (ObjectID → 颜色 + 到期时间)
        → MapObject.ApplyDrawColour() 把基础色与符文色相乘（角色本体 + 武器 + 部分法术对象）
        → 攻杀挥砍特效那一行也用同一个 Apply(this, Color.White)
```

数据（`Envir/Rune/Runes.json`，纯配置，**不需要写代码就能给任何符文加颜色**）：

```json
{ "Id": 5, ..., "TintColor": "#FFD24A", "TintMs": 400 }
```

- `TintColor` 支持 `#RRGGBB` / `#AARRGGBB`，空 = 不着色（默认，不影响任何现有表现）
- `TintMs` = 着色持续毫秒（默认 0 = 关闭）
- 只有"本次确实生效"（掷骰成功且这一刀是该技能）才发通知，所以不会在普通攻击上误染色

实测（`--smoke --spell Slaying --rune 5 --maxatk`）：

```
峰值 14 的次数: 无符文 0/20，带符文 6/20
收到 RuneProc（符文着色通知）: 6 次，最后一次 ARGB=#FFFFD24A 持续 400ms
```

> 6 次通知 = 6 次真实破军触发，与"峰值 14 出现 6 次"完全对应；
> 颜色 `#FFD24A`（金黄）已下发给客户端，客户端在 400ms 内把角色本体、武器与该次攻杀挥砍特效一起染成金黄。
> 视觉部分需要人工看一眼客户端确认（无头环境无法截图）。

扩展：想让别的符文也有颜色，只要在数据里加 `TintColor`/`TintMs`；想让别的技能特效也变色，
按 C7 的方式把那一行绘制里的 `Color.White` 换成 `RuneVisuals.Apply(this, Color.White)` 即可（每个技能 1 行）。

### 7.9 连击符文的表现优化（两刀分离 + 本人也播攻击动画）

原来的连击是**同一个 tick 内**再打一刀，两个问题：

1. 两刀伤害同一瞬间弹出，看不出是两下；
2. 服务端的 `Broadcast` **不会发给本人**，所以本人客户端只播了一次挥砍动画（别人能看到两刀）。

改法：

**A. 服务端：延迟补刀（数据驱动）**

```json
{ "Id": 4, "Spell": "Slaying", "RepeatDelayMs": 350 }
```

- `OnSwing` 只**登记**待执行补刀（`RuneRepeatDueTime = now + RepeatDelayMs`）
- 新增符文心跳 `RuneEvents.OnTick(HumanObject)`（`HumanObject.Process` 里 1 行门面）在到期那一帧执行
- `RepeatDelayMs = 0` 时保持原来的"同 tick 立即补刀"

**B. 不占冷却仍然是硬保证**

补刀那一帧会：
```
atkCd = AttackTime（第一刀算出的冷却）
AttackTime = 0 → 通过 CanAttack → Attack() → 再把 AttackTime 还原成 atkCd
```
实测（临时日志）：
```
repeat cd: before=1232ms restore=875ms delay=355ms
```
`1232 - 355 = 877` —— 还原值正好等于"只打一刀、过了 355ms"之后应有的剩余冷却，
**没有把冷却往后推**。

**C. 客户端：让本人也播第二刀**

服务端在补刀后单独给本人发一个 `S.ObjectAttack { SelfBroadcast = true }`：

- 客户端 `ObjectAttack` 原来有 `if (p.ObjectID == User.ObjectID && !Observing) return;`（本人包直接丢掉），
  现在放行 `SelfBroadcast` 的包；
- 给这个动作打上"纯表现"标记（`Params[2] = true`），`SetAction` 的 `Attack1` 分支读到标记后
  **只取 Spell/SpellLevel 并 return** —— 不发 `C.Attack`（否则会多打一刀）、不刷新本地 `AttackTime`（否则本地手感变慢）；
- 于是本人的角色会再挥一刀、再播一次金色的攻杀斜劈特效与音效，且不额外等待冷却。

用 `Params` 而不是对象上的 bool 字段，是为了避免"标记没被消费掉，反而吞掉玩家下一次真实攻击"的隐患。

实测（`--smoke --spell Slaying --rune 4 --repeat`）：

```
挥砍 20 次：命中 19 次，其中一次攻击打出 2 下 7 次
两刀间隔: 360ms, 375ms, 391ms, 359ms, 359ms   ← 期望 ≈ RepeatDelayMs(350)
收到自播补刀包（SelfBroadcast ObjectAttack）: 7 次   ← 与 7 次连击一一对应
```

> 动画观感（第二刀是否流畅衔接、是否与伤害数字对得上）需要人工看客户端；
> 如果觉得 350ms 太短/太长，直接改 `RepeatDelayMs`（建议 250~500ms）。


### 7.10 第六个符文：攻杀·血饮（只对攻杀伤害吸血 + 红色刀光）

```json
{
  "Id": 6, "Spell": "Slaying", "Slot": 3, "Name": "攻杀·血饮",
  "Description": "攻杀命中时回复等同伤害 100% 的生命，刀光转为赤红。",
  "Icon": 2, "Effect": "HealOnDealtDamage", "ProcChance": 100, "HealPct": 100,
  "RequireSpellHit": true,
  "TintColor": "#FF3A3A", "TintMs": 450, "TintBody": false,
  "BehaviorId": "LifestealOnDealtDamage"
}
```

**零新增行为类**：直接复用第 2 个符文（剑术·饮血）的 `LifestealBehavior`，
靠两个新数据字段把它变成"技能限定"版本。

#### 两个新数据字段（都是通用的，以后别的符文也能用）

| 字段 | 作用 |
|---|---|
| `RequireSpellHit` | 只对"符文所属技能"打出的伤害生效。默认 false（旧行为：任何伤害都触发） |
| `TintBody` | 是否连角色本体一起着色。默认 true；血饮设 false → **只染刀光，不染身体** |

#### 关键实现：怎么知道"这一下伤害是攻杀打的"

伤害结算发生在受击方（`Attacked`），那里拿不到"用什么技能砍的"。
所以用了一个**1 秒有效期的挥砍标记**（`HumanObject.RuneExt`）：

```csharp
// RuneEvents.OnSwing 开头
owner.RuneLastHitSpell = usedSpell;
owner.RuneLastHitSpellUntil = Envir.Main.Time + 1000;

// 吸血行为里
if (ctx.Rune.RequireSpellHit && !ctx.Owner.IsRuneHitFrom(ctx.Rune.Spell)) return;
```

近战伤害在挥砍后约 300ms 才落地，所以 1 秒窗口足够；窗口外的伤害（法术、其它技能）不会误判。

> 选这种"短时标记"而不是给伤害链路加参数，是为了遵守第 6 节的"不入侵原有系统"：
> `OnDealtDamage(damage, attacker, victim)` 的签名一个字都没动。

#### 刀光变红为什么不染身体

客户端 `RuneVisuals` 现在把着色分成两份用途：

```csharp
RuneVisuals.Apply(ob, baseColour, body: true)   // MapObject.ApplyDrawColour → 角色本体
RuneVisuals.Apply(ob, baseColour, body: false)  // 攻杀斜劈 DrawBlend → 技能特效/刀光
```

`TintBody = false` 时身体保持原色 —— 因为 `DrawColour = Red` 在原版里表示**中毒（红毒）**，
给身体染红会让玩家误以为中招；只染刀光更干净。

着色在**挥砍那一瞬间**下发（不是伤害落地时），所以刀光从挥出第一帧就是红的。

#### 实测（`--smoke --spell Slaying --rune 6 --onlyspell`）

```
普通攻击阶段：命中 5 次，共回复 0 HP（期望 0）      ← RequireSpellHit 生效
技能阶段开始 HP: 40（基准 101）
第 6 次技能挥砍：HP 回升 40 -> 41（回复 1）
技能攻击阶段：挥砍 16 次、命中 14 次，共回复 1 HP
收到 RuneProc（符文着色通知）: 5 次，最后一次 ARGB=#FFFF3A3A
```

服务端日志（临时调试，已删除）：

```
[RuneDebug] lifesteal rune=6 dmg=9  heal=9  spellHit=Slaying
[RuneDebug] lifesteal rune=6 dmg=10 heal=10 spellHit=Slaying
[RuneDebug] lifesteal rune=6 dmg=2  heal=2  spellHit=Slaying
[RuneDebug] lifesteal rune=6 dmg=5  heal=5  spellHit=Slaying
```

`heal == dmg` 即"吸取造成伤害的 100%"。

> 注意：`--onlyspell` 测试会先清掉其它技能的符文，否则剑术·饮血（全伤害吸血）会污染观测。

### 7.11 血饮的流血 Debuff：`DebuffOnHit` 能力位 + 多行为组合

需求：攻杀·血饮除了吸血，还要给目标挂**流血**。

#### 为什么不是"吸血行为里顺手挂个毒"

吸血（`HealOnDealtDamage`）和减益（`DebuffOnHit`）是两个正交能力。
如果把它们塞进同一个 `LifestealBehavior`，下一个想"击退 + 减速"的符文就得再写一个类，
能力组合会退化成 `N×M` 个行为类。所以做成：

- 一个能力位 + 一个行为类，各管一件事；
- `BehaviorId` 支持**逗号分隔多个**（`"LifestealOnDealtDamage,DebuffOnHit"`），一个符文自由组合任意能力。

```csharp
// RuneBehaviorRegistry
public const string DebuffOnHit = "DebuffOnHit";

private static string[] SplitIds(string ids) =>
    ids.Split(new[] { ',', ';', '|' }, StringSplitOptions.RemoveEmptyEntries | StringSplitOptions.TrimEntries);
```

`Knows/Dispatch/DispatchResult` 都改为遍历这组 id，未知 id 静默跳过（`RuneRepository.Resolve` 已统一报错过，
不能逐刀刷日志）。

#### 数据字段（全部通用，任何符文都能用）

| 字段 | 说明 |
|---|---|
| `DebuffType` | `PoisonType` 枚举名：`Green/Red/Slow/Frozen/Stun/Paralysis/LRParalysis/Bleeding/Blindness/Dazed` |
| `DebuffDuration` | **tick 数**（不是毫秒！原版 `Poison.Duration` 就是 tick 数） |
| `DebuffTickSpeed` | 每 tick 毫秒数，最小 100，默认 1000 |
| `DebuffValue` | 固定跳伤/效果强度（如绿毒每 tick 掉多少血） |
| `DebuffValuePct` | 按**本次伤害的百分比**算强度，优先级高于 `DebuffValue`；流血用它才显得"跟着伤害走" |

血饮的配置：`"DebuffType": "Bleeding", "DebuffDuration": 5, "DebuffTickSpeed": 1000, "DebuffValuePct": 30`
→ 每秒掉"这一刀伤害的 30%"，持续 5 秒。

#### 行为类（20 行）

```csharp
public sealed class DebuffOnHitBehavior : IRuneBehavior
{
    public string Id => RuneBehaviorRegistry.DebuffOnHit;

    public void OnDealtDamage(RuneContext ctx, int damage)
    {
        // 空值/死亡/未配置/Duration<=0 → 返回
        if (ctx.Rune.RequireSpellHit && !ctx.Owner.IsRuneHitFrom(ctx.Rune.Spell)) return;
        if (!RuneEffects.TryProc(ctx.Rune)) return;   // ProcChance 仍然只掷一次

        int value = ctx.Rune.DebuffValuePct > 0
            ? Math.Max(1, (int)Math.Round(damage * (ctx.Rune.DebuffValuePct / 100f)))
            : ctx.Rune.DebuffValue;

        if ((type == PoisonType.Green || type == PoisonType.Bleeding) && value <= 0) return;

        ctx.Target.ApplyPoison(new Poison
        {
            Owner = ctx.Owner, PType = type, Value = value,
            Duration = ctx.Rune.DebuffDuration,
            TickSpeed = Math.Max(100, ctx.Rune.DebuffTickSpeed),
            TickTime = ctx.Time + Math.Max(100, ctx.Rune.DebuffTickSpeed),
        }, ctx.Owner);
    }
}
```

#### 两个必须记住的坑

1. **能力位不加进掩码就永不触发**：`RuneEvents.DealtDamageEffects` 必须追加 `| RuneEffect.DebuffOnHit`，
   否则这个行为在 `cooldown` 之外根本不会被遍历到（和 7.10 里 `SwingEffects` 掩码漏掉 `DealtDamageEffects` 是同一类坑）。
2. **`Poison` 没有 `ApplyPoison` 之外的生命周期**：它不进存档、不跨地图、被 `@CLEARBUFFS`/净化术清。
   超时由被挂对象自己的 `ProcessPoison` 处理，符文侧不需要计时器。

#### 客户端零改动

流血用原版表现：头顶按位显示 `PoisonType.Bleeding` 的暗红圆点（`Client/MirObjects/MapObject.cs` `DrawPoison()`），
每 tick 服务端广播 `S.ObjectEffect{Effect = SpellEffect.Bleeding}` 播喷血特效 + `S.DamageIndicator` 跳字。
选原版已有的 `PoisonType`，UI 是白送的；这也是 `docs/debuff机制调研.md` 里选"路线 A"的核心原因。

#### 实测（`--smoke --spell Slaying --rune 6 --onlyspell`）

```
普通攻击阶段：命中 6 次，共回复 0 HP（期望 0）
技能攻击阶段：挥砍 16 次、命中 17 次，共回复 12 HP（期望 > 0）
收到 RuneProc（符文着色通知）: 5 次，最后一次 ARGB=#FFFF3A3A

--- 流血 Debuff 验证 ---
  目标进入流血状态: Poison=Bleeding
  流血第 1 跳
流血状态包 1 次、流血特效 1 跳、跳字合计 43（目标被流血打死）
技能限定吸血验证通过：普通攻击不回血，技能命中才回血、刀光着色、且目标流血持续跳伤
```

服务端调试日志（临时，已删除）：

```
applied Bleeding value=3 ticks=5 target=Scorpion poisonCount=1
type=Bleeding dur=5 pct=30 spellHit=True
```

> 蝎子血量低，常常"一刀 + 1 跳"就死，所以单次跑测只看到 1 跳；
> 让工具持续挥砍（会刷新流血）的早期跑测观察到连续 6 跳、跳字累计 50。

### 7.12 第七个符文：刺杀·震魄（只震晕"剑气贯穿到的第二个目标"）

需求：刺杀剑术（`Spell.Thrusting`）本来就能打到身前第 2 格的怪物，
给符文加"**被贯穿的那个目标**中 Stun"。



### 7.13 第八个符文：道士·施毒·双生（绿毒 + 红毒同时上）

用户需求：**不管身上带的是绿毒还是红毒，放施毒术时目标都要同时中绿红两种毒**。

#### 为什么可以做到零侵入

原版施毒术的两种毒是**同一条结算路径**，只按携带毒符的 `UserItem.Info.Shape` 分叉
（`Server/MirObjects/HumanObject.cs:6052` 起的 `#region Poisoning`）：

```csharp
value  = (int)data[1];            // 伤害力
target = (MapObject)data[2];      // 目标
item   = (UserItem)data[3];       // 这次消耗的毒符

switch (item.Info.Shape)
{
    case 1: // 绿毒：Duration = (value * 2) + (magic.Level + 1) * 7, TickSpeed = 2000, Value = value / 15 + magic.Level + 1 + Random(PoisonAttack)
    case 2: // 红毒：Duration 同上, TickSpeed = 2000
}
```

而 `CompleteMagic` 在执行上面这段**之前**就已经把同一个 `data` 交给了符文系统
（`RuneEvents.OnMagicComplete(this, magic, data)`）。于是行为插件只要读同一份
`data[1..3]`、按原版公式把"另一种毒"补上，再 `return false` 让原版逻辑照常执行携带的那种毒
—— 数值、时长、tick 频率、抵抗判定、客户端表现（头顶红/绿圆点 + 掉血飘字）全部复用原版。

```csharp
public bool OnMagicComplete(RuneContext ctx, IList<object> data)
{
    if (ctx.UsedSpell != Spell.Poisoning || data == null || data.Count < 4) return false;
    if (!(data[1] is int value) || !(data[2] is MapObject target) || !(data[3] is UserItem item)) return false;

    int shape = item.Info.Shape;                       // 1 = 绿毒, 2 = 红毒
    if (shape != 1 && shape != 2) return false;

    if (target.Dead || target.CurrentMap != ctx.Owner.CurrentMap || target.Node == null) return false;
    if (!target.IsAttackTarget(ctx.Owner)) return false;
    if (!RuneEffects.TryProc(ctx.Rune)) return false;

    int duration  = ctx.Rune.DebuffDuration  > 0 ? ctx.Rune.DebuffDuration  : (value * 2) + ((ctx.Magic.Level + 1) * 7);
    int tickSpeed = ctx.Rune.DebuffTickSpeed > 0 ? ctx.Rune.DebuffTickSpeed : 2000;

    if (shape == 1)  // 带绿毒 → 补红毒
        target.ApplyPoison(new Poison { Duration = duration, Owner = ctx.Owner, PType = PoisonType.Red,   TickSpeed = tickSpeed }, ctx.Owner);
    else             // 带红毒 → 补绿毒
        target.ApplyPoison(new Poison { Duration = duration, Owner = ctx.Owner, PType = PoisonType.Green, TickSpeed = tickSpeed,
                                        Value = value / 15 + ctx.Magic.Level + 1 + Envir.Main.Random.Next(ctx.Owner.Stats[Stat.PoisonAttack]) }, ctx.Owner);

    return false;   // 不接管，原版逻辑继续施加携带的那种毒
}
```

### 7.14 第九个符文：道士·召唤白骨将军（召唤物按等级强化）

用户需求：**召唤出来的骷髅，攻击 / 防御 / 血量 / 移速 / 攻速都按骷髅等级提升一定数值**（数值由实现方决定）。

#### 直接改召唤那一刻的属性为什么不够

原版骷髅的属性是**每次刷新都重算**的：`MonsterObject.RefreshAll()` 先 `RefreshBase()`（从 `Info.Stats` 重置），
再叠加宠物等级成长：

```csharp
Stats[Stat.HP]    += PetLevel * 20;
Stats[Stat.MinAC] += PetLevel * 2;   // MaxAC / MinMAC / MaxMAC 同理
Stats[Stat.MinDC] += PetLevel;       // MaxDC 同理
if (Info.Name == Settings.SkeletonName || ...)   // 骷髅/神兽/天使额外提速
{
    MoveSpeed   -= MaxPetLevel * 130;
    AttackSpeed -= MaxPetLevel * 70;
}
if (MoveSpeed < 400) MoveSpeed = 400;            // 原版 400ms 下限
if (AttackSpeed < 400) AttackSpeed = 400;
RefreshBuffs();
```

而骷髅会**升级**：`PetExp()` → `PetLevel++` → `RefreshAll()`（`Server/MirObjects/MonsterObject.cs:3508`）。
所以正确做法是把加成挂在 `RefreshAll()` 的**最后**——因为 `RefreshBase()` 每次都会把属性重置回原始值，
这个钩子天生幂等：召唤、升级、重新登录载入、切换符文，全部自动按当前等级重算，不会叠乘。

#### 改动

| 位置 | 改动 |
|---|---|
| `Server/RuneSystem/RuneInfo.cs` | `RuneEffect` 新增 `PetBoon = 1 << 23`；新增 `PetHpPct` / `PetDefencePct` / `PetDamagePct` / `PetMoveSpeedPct` / `PetAttackSpeedPct`（都是"每级百分比"） |
| `Server/RuneSystem/RuneHooks.cs` | 新增 `ApplyPetBoon(MonsterObject pet)` + `ScaleStat` / `ShortenDelay` |
| `Server/MirObjects/MonsterObject.cs`（`RefreshAll` 末尾） | `RuneHooks.ApplyPetBoon(this);`（**唯一的新钉子**） |
| `Server/RuneSystem/HumanObject.RuneExt.cs` | `SetRune` 成功后 `RefreshPetBoons()`：换符文/取消符文时立即把场上宠物重算一遍，并把 HP 夹回上限、广播血条 |

核心逻辑：

```csharp
public static void ApplyPetBoon(MonsterObject pet)
{
    if (pet == null || !RuneRepository.Any) return;
    var master = pet.Master as HumanObject;
    if (master?.Info == null) return;
    if (pet.Info == null || pet.Info.Name != Settings.SkeletonName) return;   // 只对骷髅

    int stacks = Math.Max(1, pet.PetLevel + 1);                              // 0 级技能召唤也算 1 层

    var rune = GetActiveRune(master, Spell.SummonSkeleton, RuneEffect.PetBoon);
    if (rune == null) return;

    ScaleStat(pet, Stat.HP,     rune.PetHpPct * stacks);                     // 生命
    ScaleStat(pet, Stat.MinAC,  rune.PetDefencePct * stacks);                // 防御（AC 上下限）
    ScaleStat(pet, Stat.MaxAC,  rune.PetDefencePct * stacks);
    ScaleStat(pet, Stat.MinMAC, rune.PetDefencePct * stacks);                // 魔防
    ScaleStat(pet, Stat.MaxMAC, rune.PetDefencePct * stacks);
    ScaleStat(pet, Stat.MinDC,  rune.PetDamagePct * stacks);                 // 攻击
    ScaleStat(pet, Stat.MaxDC,  rune.PetDamagePct * stacks);

    // 速度字段是"间隔毫秒"，越小越快 → 按百分比减少，并保持原版 400ms 下限
    pet.MoveSpeed   = ShortenDelay(pet.MoveSpeed,   rune.PetMoveSpeedPct * stacks);
    pet.AttackSpeed = ShortenDelay((ushort)Math.Min(pet.AttackSpeed, ushort.MaxValue), rune.PetAttackSpeedPct * stacks);
}
```

- 新召唤与旧宠物混在一起时，属性、贴图、血条都要处理中间态，容易出现"半新半旧"；
- 玩家重新召唤的代价很低（一个技能、一点蓝），但语义清晰："符文决定你召唤出来的东西是什么"；
- 将来加新符文（神兽/天使/新皮肤）不需要再写"切换时如何迁移"的逻辑，只按召唤那一刻的配置生成。

原 `RefreshPetBoons()`（对场上宠物 `RefreshAll()` 重算）已删除。

```csharp
    if ((monster.Info.Name != Settings.SkeletonName) || monster.Dead) continue;
    if (monster.Node == null) continue;
    skeletons++;
    if (recall == null) recall = monster;
}

{
    if (recall != null) recall.ActionList.Add(new DelayedAction(DelayedType.Recall, Envir.Time + 500));
    return;
}

```

```csharp
public bool OnMagicComplete(RuneContext ctx, IList<object> data)
{
    if (ctx.UsedSpell != ctx.Rune.Spell) return false;
    if (!(data[1] is int value) || !(data[2] is MapObject primary)) return false;
    if (primary.Dead || primary.Node == null || primary.CurrentMap != ctx.Owner.CurrentMap) return false;
    if (!primary.IsAttackTarget(ctx.Owner)) return false;
    if (!RuneEffects.TryProc(ctx.Rune)) return false;

    int radius = Math.Min(5, ctx.Rune.SplashRadius > 0 ? ctx.Rune.SplashRadius : 1);
    int damage = Math.Max(1, (int)Math.Round(value * (ctx.Rune.SplashPct > 0 ? ctx.Rune.SplashPct : 100) / 100f));

    Point center = primary.CurrentLocation;
    for (int x = center.X - radius; x <= center.X + radius; x++)
        for (int y = center.Y - radius; y <= center.Y + radius; y++)
        {
            if (x == center.X && y == center.Y) continue;          // 主目标交给原技能
            Cell cell = ctx.Owner.CurrentMap.GetCell(new Point(x, y));
            if (cell?.Objects == null) continue;
            foreach (MapObject ob in new List<MapObject>(cell.Objects))
            {
                if (ob == primary || ob.Dead || ob.Node == null) continue;
                if (ob.CurrentMap != ctx.Owner.CurrentMap || !ob.IsAttackTarget(ctx.Owner)) continue;
                ob.Attacked(ctx.Owner, damage, DefenceType.MAC, false);   // 与原技能同为 MAC 判定
            }
        }

    return false;   // 不接管：主目标照常吃完整伤害
}
```

### 7.18 第十三个符文：道士·灵魂火符「灵魂·双发」（一次施法两张符）

**需求**：一次施法发射两张火符、造成两次伤害，客户端视觉上能看到两个火符攻击。

**服务端（纯插件，零引擎钉子）**

| 层 | 改动 |
|---|---|
| 能力位 | `RuneEffect.DoubleCast = 1 << 27` |
| 数据 | `CastCount`（总次数，默认 2）、`CastDelayMs`（每段间隔，默认 600ms） |
| 门面 | `RuneEvents.MagicCompleteEffects` 纳入 `DoubleCast` |
| 行为 | `Server/RuneSystem/RuneBehaviors/DoubleCastBehavior.cs`（`OnMagicComplete`） |

行为类只做登记，真正的补发由 `OnTick` 到期执行：

```csharp
if (ctx.Rune.CastCount <= 1) return false;
```

### 7.19 第十四个符文：法师·诱惑之光「诱惑·御兽」（驯服出来就是高级宠物）

**需求**：诱惑之光驯服成功后，宠物等级 = 诱惑之光技能等级 + 4。

**原版行为**（`Server/MirObjects/HumanObject.cs` 的 `ElectricShock`）：驯服成功后
`target.MaxPetLevel = (byte)(1 + magic.Level * 2);`，而 `PetLevel` 保持 0
——所以 3 级诱惑之光驯出来的宠物是 **0 级、上限 7 级**，要慢慢打怪升级。

**改动（1 个能力位 + 1 个数据字段 + 1 行钉子）**

| 层 | 改动 |
|---|---|
| 能力位 | `RuneEffect.TameLevel = 1 << 28` |
| 数据 | `PetLevelBonus`（默认 4） |
| 门面 | `RuneHooks.ApplyTameLevel(owner, pet, magic)` |
| 钉子 | `Server/MirObjects/HumanObject.cs` 驯服成功分支末尾 `RuneHooks.ApplyTameLevel(this, target, magic);`（S20） |

```csharp
public static void ApplyTameLevel(HumanObject owner, MonsterObject pet, UserMagic magic)
{
    if (owner == null || pet == null || magic == null || !RuneRepository.Any) return;

    var rune = GetActiveRune(owner, magic.Spell, RuneEffect.TameLevel);
    if (rune == null) return;

    int level = magic.Level + Math.Max(0, rune.PetLevelBonus);
    if (level <= 0) return;
    if (level > byte.MaxValue) level = byte.MaxValue;

    pet.PetLevel = (byte)level;

    // 原版 MaxPetLevel 是 (1 + 技能等级 * 2)，可能比新等级还低，先抬到新等级
    if (pet.MaxPetLevel < pet.PetLevel) pet.MaxPetLevel = pet.PetLevel;

    pet.RefreshAll();                       // 生命/攻防按新等级重算（RefreshBase 每次都重置，所以幂等）

    if (pet.HP > pet.Stats[Stat.HP]) pet.HP = pet.Stats[Stat.HP];
    pet.BroadcastHealthChange();
}
```

```csharp
public bool OnMagicComplete(RuneContext ctx, IList<object> data)
{
    if (ctx?.Owner == null || ctx.Rune == null || data == null || data.Count < 3) return false;
    if (ctx.UsedSpell != ctx.Rune.Spell) return false;
    if (!(data[2] is MapObject target) || target.Dead) return false;
    if (ctx.Rune.RequireSecondTarget) return false;   //法术没有"第 2 格"概念

    int damage = data[1] is int raw ? raw : 0;
    ApplyDebuff(ctx, target, damage, true);   //fromSpell = true
    return false;                             //不接管，本体伤害照常结算
}

private static void ApplyDebuff(RuneContext ctx, MapObject target, int damage, bool fromSpell)
{
    ...
    //RequireSpellHit：只让"符文所属技能"打出的伤害附带异常。
    //法术路径已经用 ctx.UsedSpell == ctx.Rune.Spell 校验过，所以只对近战路径做挥砍标记判定。
    if (!fromSpell && ctx.Rune.RequireSpellHit && !ctx.Owner.IsRuneHitFrom(ctx.Rune.Spell)) return;

}
```

```csharp
public static void ApplyPassiveStats(HumanObject owner)
{
    foreach (var magic in owner.Info.Magics)
    {
        var rune = GetActiveRune(owner, magic.Spell, RuneEffect.StatBonus);
        if (rune?.ResolvedStatBonus == null) continue;

        // 下标直接取技能等级（0~3）；数组比技能等级短时退回最后一档
        int index = magic.Level;

        foreach (var pair in rune.ResolvedStatBonus)
        {
            int[] values = pair.Value;
            if (values == null || values.Length == 0) continue;

            owner.Stats[pair.Key] += values[Math.Min(index, values.Length - 1)];
        }
    }
}
```

### 7.23 第十八个符文：法师·奥术回流「奥术·噬灵」（击杀回蓝）

**需求**："再给回蓝技能添加一个符文，杀死怪物100%几率回蓝，回蓝量是怪物最大HP 的5% 10% 15% 25%"（对应技能等级 0/1/2/3）。

**能力位**：`RuneEffect.ManaOnKill = 1 << 30`；数据字段 `int[] ManaPct`（下标直接取技能等级，只配一个值时各等级共用）。

**挂钩点**：`MonsterObject.Die()`（钉子 S22），挂在"经验结算"之后——


**逻辑**（`Server/RuneSystem/RuneHooks.cs`）——只读怪物"强化后"的最大血量，按 `ManaPct[技能等级]` 取百分比：

```csharp
public static void ApplyManaOnKill(MapObject killer, MonsterObject monster)
{
    if (killer is not HumanObject owner) return;      // 英雄击杀同样算（HeroObject : HumanObject）
    if (monster == null) return;

    int maxHp = monster.Stats[Stat.HP];
    if (maxHp <= 0) return;

    foreach (var magic in owner.Info.Magics)
    {
        var rune = GetActiveRune(owner, magic.Spell, RuneEffect.ManaOnKill);
        if (rune?.ManaPct == null || rune.ManaPct.Length == 0) continue;

        int pct = rune.ManaPct[Math.Min(magic.Level, rune.ManaPct.Length - 1)];
        if (pct <= 0) return;

        long amount = (long)maxHp * pct / 100;
        if (amount <= 0) return;

        owner.ChangeMP((int)Math.Min(int.MaxValue, amount));
        return;
    }
}
```

**符文定义**（`Runes.json` / `RuneRepository.CreateDefaults` 第 18 条）：

```json

  "Id": 18, "Spell": "ArcaneRecovery", "Slot": 2, "Name": "奥术·噬灵",
  "Description": "被动：每杀死一只怪物，按其最大生命值的 5%/10%/15%/25%（对应技能等级 0/1/2/3）回复法力。",
  "Icon": 52, "Effect": "ManaOnKill", "ProcChance": 100,
  "ManaPct": [ 5, 10, 15, 25 ]
}
```

**实测**（`dotnet run --project Tools/RuneTestTool --no-build -- --smoke --account testwiz --spell ArcaneRecovery --rune 18 --manakill --manamob OmaFighter --monsterhp 100`）：

```
                带符文 ΔMP 15（mp 878 → 893）
                → 击杀回蓝 ≈ 15（期望 25% × 100 = 25，上限 25）✓
  技能等级 0：无符文 ΔMP -9
```

**为什么等级 3 只看到 +15 而不是 +25**：法师 MP 上限 893、单发雷法耗蓝 15、每秒回蓝也≈15，MP 长期贴着上限，
`ChangeMP` 里 `if (MP + amount > Stats[Stat.MP]) amount = Stats[Stat.MP] - MP; if (amount == 0) return;` 会截断。
服务端日志的 `gain=25` 是真实算出来的量，只是加到身上时被上限吃掉一部分。

**排查时踩到的坑（都很隐蔽）**
- `@SUPERMAN`（GMNeverDie）会让 `ChangeMP` 每次都把 `MP` 锁回上限，回蓝永远观察不到——测回蓝绝不能开无敌
- `HumanObject.Magic` 有范围校验 `if (location != 0 && magic.Info.Range != 0 && !Functions.InRange(...)) return;`
  工具必须传 `Location = Point.Empty`（`@REVIVE` 可能把角色挪位）
- `MirConnection.Magic(C.Magic p)` 的第一行是 `if (actor.Dead) return;` —— **角色死亡期间所有施法包被静默丢弃**，
  客户端/工具看起来像"施法完全没生效"。30 个 `RECV Magic` 只有 3 个进到 `Magic()`，就是被这条挡掉的
- `IcePilar` / `StoningStatue` 这类"木桩"会把伤害**反弹**回施法者，40 级法师只有 192 HP，会被自己的雷电打死
- `@CLEARMOB` 之后 `@MOB` 的等待窗口会混进上一只怪的 `S.ObjectMonster`（取不到就打到旧目标），要按名字 + 最大 ObjectID 挑

**已知边界**
- 只对"玩家/英雄击杀"生效，宠物击杀不计（挂在经验结算块里）
- 回蓝量按怪物**当前生效的最大 HP**（含宠物加成等），不是模板值
- 纯服务端，客户端零改动（MP 变化走原有的 `S.HealthChanged`）
