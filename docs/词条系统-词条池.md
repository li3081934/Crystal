# 词条池设计（暗黑2 词缀 → Mir 属性）

> 配套文档：[词条系统-设计方案.md](词条系统-设计方案.md)（数据模型、生成流程、客户端展示、PR 划分）。
> 本文只解决一件事：**词条池里到底放哪些词条、数值多大、落在哪些部位**。

版本：v1（2026-11-12）
数据来源：暗黑2 词缀表（D2R LoD，PlanetDiablo D2 数据库的戒指/项链/防具词缀表）+ 本仓库 `Stat` / `BaseStats` / 现有装备数值。

---

## 0. 摘要

- 暗黑2 的词缀体系 = **词族（Group）+ 档位（Level）+ 数值区间 + 部位/等级门槛**；同一族的名字随档位升级（Lizard's → Snake's → Serpent's → Drake's … Bahamut's），本质是"一条属性、多档数值"。
- 本仓库可直接承接的属性有 **40 个左右**（攻击/防御/生命魔法/准确敏捷/攻速/暴击/吸血/抗性/恢复/掉率/负重/减伤），
  无法承接的有 **力量/敏捷/精力三围、法力偷取、施法速度(FCR)、移动速度、技能等级、元素伤害与元素抗性**（详见 §3.2）。
- 词条池设计成 **56 个词族 × 5 档 = 280 条定义**：前缀 28 族（输出/收益向）、后缀 28 族（防御/属性向），全部使用 `Stat` 枚举里的既有值，**不新增 Stat**。
- 一档一条 `AffixInfo`（与设计方案 §4.1 一致），ID 规则：`前缀 1xxx`、`后缀 2xxx`，`Id = 基数 + 族号×10 + 档位`；见 §4。
- 数值按"同部位、同档位、同属性"横向可比来标定；T5 单条强度约等于一件中档装备的该属性，四条 T5 不至于直接破平衡（§7）。
- 与暗黑2 的差异集中在"没有三围/没有 FCR"，这部分用 **准确/攻速/负重/掉率** 做了语义替代，见 §3.2 的映射表。

---

## 1. 目标与边界

### 1.1 目标

1. 词条是**独立于现有六套改造系统**的第二属性层（`UserItem.Affixes`），不写 `AddedStats`、不参与精炼惩罚。
2. 词条有**前后缀、有档位、按怪物等级（ilvl）出场**，读起来像暗黑2。
3. 首版词条池**一次给全**，后续加玩法（洗练/升档/转移）只改 `AffixService`，不用重排 ID。

### 1.2 边界

| 项 | 结论 |
|---|---|
| 是否改 `Stat` 枚举 | **不改**。只用已定义值，`AffixRepository.Load()` 用 `Enum.IsDefined` 校验 |
| 是否改 `ItemGrade` | 不改，沿用 None/Common/Rare/Legendary/Mythical/Heroic 作为词条数量依据 |
| 是否影响摆摊/聊天/日志 | 不影响：装备名不变（决策见设计方案 §4.3） |
| 首版是否做洗练 | 不做，但 `AffixIlvl` / `Flags` / `Reroll` 接口预留 |

## 2. 暗黑2 词缀体系速览

### 2.1 数据结构

D2 每条词缀的字段（以戒指/项链表为例）：

```
Name       词形名，如 Lizard's / of the Jackal
Group      词族编号，同族的不同档位共享
Level      词缀等级 1–99（决定它什么时候能出）
Level req  装备需求等级
freq       抽取频率（权重）
Stats      数值区间，如 +1 to +2 to Mana
```

### 2.2 分布规模（D2R 戒指/项链）

| 部位 | magic 前缀 | magic 后缀 | rare 前缀 | rare 后缀 |
|---|---|---|---|---|
| 戒指 Ring | 41 个 / 总频率 116 | 38 / 118 | 34 / 102 | 32 / 96 |
| 项链 Amulet | 110 / 238 | 89 / 255 | 89 / 211 | 78 / 221 |

规律：

- **前缀偏"攻/资源/抗性"，后缀偏"属性/吸血/收益"**（不是绝对，但足够做本仓库的取舍依据）。
- 同一词族按 `Level` 分 3–8 段，数值逐段放大；高档词条只在 ilvl 很高时出现。
- 一件 rare 最多 3 前缀 + 3 后缀（crafted 最多 3+3），magic 只有 1+1。

### 2.3 主要词族（与本仓库相关的部分）

| 分类 | D2 词族示例 | 数值跨度 |
|---|---|---|
| 攻击准确 | Bronze→Platinum(+AR)、of Craftmanship/Maiming(+最大伤)、of Worth→Performance(+最小伤) | AR 10–120、伤害 +1–13 |
| 生命魔法 | Lizard's→Bahamut's(+法力)、of the Jackal→Whale(+生命)、of Regeneration→Revivification(回血) | 法力 1–120、生命 1–100、回血 2–15 |
| 三围 | of Strength→Atlas、of Dexterity→Nirvana、of Energy→Enlightenment | +1–30 |
| 抗性 | Azure/Lapis/Cobalt/Sapphire(冰)、Crimson/Russet/Garnet/Ruby(火)、Tangerine/Ocher/Coral/Amber(电)、Beryl/Viridian/Jade/Emerald(毒)、Shimmering→Chromatic(全抗) | 单抗 5–40%、全抗 3–30% |
| 吸血 | of the Leech/Locust/Lamprey(生命偷取)、of the Bat/Wraith/Vampire(法力偷取) | 2–8% |
| 收益 | of Greed/Wealth(金币)、Felicitous/Fortuitous/of Chance→Luck(MF) | 金币 25–80%、MF 5–35% |
| 减伤 | of Health→Life Everlasting(物免)、of Warding→Negation(法免)、Vulpine(伤害转法力) | 物免 1–25、法免 1–6 |
| 速度 | of the Apprentice(+10% FCR)、of Alacrity 系列(IAS) | FCR 10%、IAS 10–20% |
| 其它 | of Thawing(冰冻减半)、of Remedy/Amelioration/Defiance(毒时长 -25/50/75%)、+技能等级族、聚气/触发族 | — |

### 3.2 无法承接的 D2 词族与替代方案

| D2 词族 | 本仓库现状 | 替代方案 |
|---|---|---|
| +力量 Strength | `Stat` 里没有力量；`Stat.Strong` 是**耐久强化**（且只对武器生效） | 映射为 `WearWeight`（穿戴负重），词形仍可用"之巨力"；或直接不进池 |
| +敏捷 Dexterity | 没有 Dex；`Agility` 是闪避 | 映射为 `Agility`，词形"之疾风" |
| +精力 Energy | 没有 Energy | 映射为 `MP` / `MPRatePercent` |
| +法力偷取 Mana Leech | 没有 `MPDrainRatePercent` | 不做；未来若加 Stat 再补（ID 段留空 1051 之后不占） |
| 施法速度 FCR | 没有 `CastSpeed`，全局 1800ms 写死 | 不做；用 `AttackSpeed` 不能替代（只影响近战）。若将来加 `CastSpeed`，走新增 Stat + 新 ID 段 |
| 移动速度 FRW | 没有移速 Stat（`MoveDelay` 常量 600） | 不做 |
| +技能等级 | 没有技能等级加成机制（符文系统才有 `NeedMagicLevel` 门槛） | 不做；用 `SkillGainMultiplier`（技能经验）做弱化版 |
| 元素伤害/元素抗性（火冰电） | 只有 `MagicResist` / `PoisonResist`；伤害类型只有 物理/魔法/道术/毒 | 火冰电统一并入"魔法抗性"，但 **Caps=2** 导致数值极小；因此抗性词条只做 `MagicResist`(+1/+2) 与 `PoisonResist`(+1..+6) 两族 |
| 光照/耐力/击退/压碎性打击/撕开伤口 | 无对应机制 | 不做 |

> 结论：**词条池不追求"1:1 复刻"，而是"同名同感 + 同量级"**。凡是会引入新 Stat 的族一律不进首版，避免动 `Stat` 枚举、`RefreshStatCaps`、客户端 `RefreshStats` 三处联动。

## 4. ID、档位与命名

### 4.1 ID 规则

```
前缀：1000 + 族号×10 + 档位     族号 0..27  → 1001..1005, 1011..1015, … 1271..1275
后缀：2000 + 族号×10 + 档位     族号 0..27  → 2001..2005, 2011..2015, … 2271..2275
```

- 一个**词族**占 10 个号（5 档 + 5 个预留），便于将来加 T6 或加变体。
- `AffixInfo.Group` 填族名（如 `"MaxDC"` 不行，同名属性有多族；用 `"p_dmg_flat"` 这类稳定串），同 Group 互斥。
- `Name` 就是展示词形；`NameKey = "Affix_" + Id`，客户端优先查翻译表，缺失回退 `Name`。
- **一档一条定义**（`Tier` 1..5），这是对设计方案 §4.1 的落地口径；设计方案附录 B 的"一行三档"表格按本文改写。

### 4.2 档位与 ilvl

| 档位 | MinIlvl | 大致对应 | 说明 |
|---|---|---|---|
| T1 | 1 | 新手图 | 只有小数值 |
| T2 | 21 | 中期 | — |
| T3 | 41 | 中后期 | 开始出"大词条" |
| T4 | 61 | 高级图 | — |
| T5 | 81 | 顶级图 | 单条接近中档装备 |

掷骰时 `MinIlvl <= ilvl` 的档位里取**最高档**（不是随机档），保证高等级装备不会掉出 T1。

### 4.3 词形规范

- 前缀：`形容词 + 的`，如 `凶残的`、`坚固的`、`幸运的`。
- 后缀：`之 + 名词`，如 `之熊`、`之烈焰`、`之生命`。
- 同一属性在前缀/后缀各有一族时，词形必须不同（例：`凶残的`=MaxDC 前缀，`之熊`=MaxDC 后缀），否则提示框里会出现两条同名。
- 词形不并入装备名（设计方案 §4.3 的决策），只在 tooltip 行与名字染色里体现。

## 6. 抽取规则（与设计方案 §5 对齐）

### 6.1 词条数量

| ItemGrade | 词条数 | 前缀配额 | 后缀配额 |
|---|---|---|---|
| None / Common | 0 | — | — |
| Rare | 2 | 1 | 1 |
| Legendary | 3 | 2 | 1 |
| Mythical | 4 | 2 | 2 |
| Heroic | 4 | 2 | 2 |

补充规则：

- ilvl ≥ 60 的白装（None）额外 10% 概率补 1 条（只补 T3 以下），让高图白装也有惊喜。
- 总数受 `MaxPerItem`（每族 1）与 `Group` 互斥约束；如果候选池不足，允许少出（`TryRoll` 里 `continue`）。
- 同一件装备不会出现两条同 `Group`（例如不会同时有 `凶残的` 和 `之熊` 吗？——**会**，它们 Group 不同，一条是 `p_maxdc_flat`、一条是 `s_maxdc_flat`，这正是设计意图：前缀给大数值、后缀给小数值，两者可以叠）。

### 6.2 权重

- 权重按"同部位同类型（前/后）"归一化后加权抽取（`WeightedPick`）。
- 数值越强的族权重越低：基础输出族 100，暴击/吸血 30–50，比例类 15–20。
- 高 Tier 不额外降权（D2 也不降），靠 `MinIlvl` 门槛控制出场。

### 6.3 互斥

- `Excludes` 首版留空；同 `Group` 天然互斥。
- 未来若要"同一属性只能一条"，用 `Excludes` 把 `p_maxdc_flat` 与 `s_maxdc_flat` 互相排除即可，不改数据结构。

## 7. 数值校准

### 7.1 校准基准

| 参照 | 数值 |
|---|---|
| 属性 Caps（`BaseStats.cs:91-99`） | MagicResist 2、PoisonResist 6、CriticalRate 18、CriticalDamage 10、Freezing 6、PoisonAttack 6、HealthRecovery 8、SpellRecovery 8、PoisonRecovery 6 |
| 战斗权重 | CriticalRateWeight 5（暴击率 = 值×5%）、CriticalDamageWeight 50（暴伤 = 值/50×10） |
| 攻速公式 | `1400-(AS*60+min(370,Level*14))`，下限 550 → 3 点攻速 = 180ms |
| 命中 | `Random.Next(Agility+1) > Accuracy` → Accuracy 每 +1 都是显著提升，故单条上限 10 |

### 7.2 标定原则

1. **单条 T5 ≈ 一件中档同部位装备的该属性**（例：T5 武器 MaxDC +14~18，中档武器 DC 约 5–20）。
2. **四条 T5 同时出现 ≈ 一件顶级装备的差距**，不构成碾压（对比现有"+7 装备"体系）。
3. `MagicResist` 因 Caps=2，只给 +1/+2，且只有 T4/T5 才给 2。
4. `CriticalRate`/`CriticalDamage`/`Freezing`/`PoisonAttack` 受 Caps 约束，T5 也压在 Caps 的 1/3 以内，避免单件顶满。
5. 百分比类（`HPRatePercent`/`MPRatePercent`/`AttackSpeedRatePercent`）单条最高 5–6%，避免与 Buff/技能乘算爆炸。

### 7.3 待实测项

- [ ] T5 四条全出时，战士/法师/道士各一场 Boss 战的 TTK 变化（目标：±15% 内）。
- [ ] `GoldDropRatePercent` 与 `ItemDropRatePercent` 叠加后，`DropInfo.AttemptDrop` 的实际收益（这两个值直接进掉落加成）。
- [ ] `HPDrainRatePercent` 与吸血武器叠加后的续航（公式 `(damage-armour)/100*value`）。
- [ ] `WearWeight`/`BagWeight` 词条与 `SpecialItemMode.Muscle`、套装加成的叠加是否越界。

### 7.4 百分比词条的计算顺序（实现约束）

`HPRatePercent` / `MPRatePercent` / `AttackSpeedRatePercent` / `MaxDCRatePercent` 这些「率」类词条，**必须在百分比放大之前**计入 `Stats`，否则本帧无效：

- 服务端：`RefreshStats()`（`HumanObject.cs:1783`）先调 `RefreshEquipmentStats()`（:1795，内部 :1913 `Stats.Add(realItem.Stats)`、:1914 `Stats.Add(temp.AddedStats)`、:1916-1929 觉醒、:1946 `RefreshSocketStats`），再执行 :1804-1812 的百分比放大。词条要么在 :1914 旁边 `AffixService.Apply(temp, Stats)`，要么在 `RefreshEquipmentStats()` 之后、:1804 之前插一个 `RefreshAffixStats()` 调用。
- 客户端：`UserObject.RefreshStats()`（:144）先调 `RefreshEquipmentStats()`（:150，内部 :281 `Stats.Add(temp.AddedStats)`、:309 `RefreshSocketStats`），再执行 :161-169 的放大。同理，插在 :150 之后、:161 之前即可（设计稿的「与 `RefreshEquipmentStats()` 并列」正好满足）。

> 一句话：**只要在百分比放大（服务端 :1804-1812 / 客户端 :161-169）之前计入就行**；如果图省事写成 `RefreshStatCaps()` 之后，率类词条会静默失效，而且不报错。

## 附录 B：新增词族的检查清单

新增一族时按顺序确认：

1. `Stat` 在 `Shared/Data/Stat.cs` 里存在，且**不新增枚举值**（新增会牵动 `RefreshStatCaps`、客户端 `RefreshStats`、存档兼容）。
2. 数值是否受 Caps 约束（查 `Shared/BaseStats.cs:91-99`），若受约束，T5 不超过 Caps 的 1/3。
3. 部位 `Slots` 是否与 `ItemType` 里真实存在的类型一致（`Amulet` 是消耗品，不是首饰，别放进去）。
4. 前缀/后缀词形是否与既有族重名（重名会让 tooltip 出现两条同样的名字）。
5. 权重是否与"同部位同类型"的其它族可比（基础输出 100，比例类 15–20）。
6. 是否需要 `Excludes`（默认空，靠 Group 互斥）。
7. 同步 `Client/Localization/Chinese.json` 的 `Affix_<Id>` 键（缺失会回退 `Name`，不会崩）。
